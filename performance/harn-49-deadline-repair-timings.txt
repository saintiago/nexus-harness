HARN-49, second round: the two cases the last gate stopped on
===========================================================

Recorded 2026-09-22 on the Windows host used for this whole task (24 logical CPUs, Node v24.14.1,
npm 11.11.0, Vitest 5.0.0). Both measurements select one case per run, with the boundary project's
own four-worker cap in force, and report the duration Vitest records for the case:

   $ npx vitest run --project boundary tests/completion-arm.test.ts \
       -t "finishes an already-merged admission" --reporter=json --outputFile=…
   $ npx vitest run --project boundary tests/completion-github.test.ts \
       -t "creates the per-issue evidence directory" --reporter=json --outputFile=…

1. Before the repair, with the stand-in `gh` behind a `.cmd` shim
-----------------------------------------------------------------

   arm case (finishes an already-merged admission without arming or asking for a person)
      3,000 ms
   github case (creates the per-issue evidence directory before its first GitHub command)
      2,485 ms

   For comparison, the same two cases inside a full four-worker boundary-layer run on this host:
   3,536 ms and 2,524 ms, with the layer itself at 275.34 s over 37 files.

2. After the repair, with the stand-in as one process
-----------------------------------------------------

   arm case      2,144 ms / 2,238 ms   (two runs)
   github case   1,578 ms / 1,669 ms   (two runs)

   A full four-worker boundary-layer run of the repaired revision, JSON-timed: 37 files, 802 passed,
   2 skipped, the layer at 237.30 s, and the two cases at 4,039 ms and 2,430 ms inside it. Those two
   in-layer numbers are host-load readings on a shared machine (the same run's other files moved the
   same way); the isolated pairs above are the controlled comparison, same commands, same host, one
   case per run, and they are what the 28–37% reduction is measured from.

3. No deadline changed
----------------------

   `vitest.config.ts` states no `testTimeout` for either project, so every case keeps Vitest's
   five-second default unless it states a bound of its own. The measured seven-second probe and the
   15 s `BOUNDARY_DEFAULT_TIMEOUT_MS` that the previous round added were withdrawn; they remain on
   the record in `harn-49-boundary-timeout-repair.txt`. `tests/validation-cache.test.ts` fails if a
   shared `testTimeout` appears in the configuration again.

   The same one-process shape was adopted by the two `tests/queue-cli.test.ts` cases that drive the
   completion stand-in: inside the same layer runs they measured 5,790 ms and 4,350 ms before, and
   4,601 ms and 3,171 ms after. Neither case states its own bound less than 30 s.
